# 下单链路压测报告（2026-10-28 ～ 10-29）

> 状态：**定稿**。共 9 轮，压测脚本和使用说明在 [tests/load/](../tests/load/README.md)。

## 1. 环境与方法

| 项 | 说明 |
|---|---|
| 服务器 | 单台 4 核 8G，5Mbps 公网带宽，Ubuntu，Docker Compose；后期加了 4G swap |
| 部署 | 14 个 .NET 服务（含 YARP 网关、BFF）+ PostgreSQL + RabbitMQ + Redis + 监控（OTel Collector / Prometheus / Loki / Tempo / Grafana）全部同机；R3 起停掉了 Elasticsearch 和搜索服务 |
| 压测机 | 本机 k6，经公网 HTTPS 访问，路径与真实用户一致：nginx → BFF.Web（Cookie 会话）→ 网关 → 订单服务 |
| 用户 | 2000 个测试账号，`prepare.mjs` 走真实授权码 + PKCE 登录后导出会话；余额支付 |
| 场景 | `ramping-arrival-rate`，阶梯 `1m:50 → 2m:100 → 2m:200 → 1m:0`（每秒到达请求数），6 分钟；R7 起下单前先预热，每个用户 GET 一次，刷新过期令牌 |
| 商品 | R1～R8 只用一两个 SKU；R9 用 30 个 SKU（`tests/load/skus.txt`，不入库），库存充足 |
| 观测 | k6 汇总 + 网页面板导出、Grafana（PG 连接池、线程池、GC、RabbitMQ 队列与发布速率）、Tempo 链路、各库 Outbox 表 |

**口径**：下单接口返回 202 只代表"已受理"，后面的库存预占、支付、确认都是异步的。所以除了 k6 的受理数据，还要看 Outbox 待发布数和 RabbitMQ 队列堆积，判断后台能不能跟上。R4 起有全局并发上限，过载时多出的请求返回 429，所以"受理成功/秒"要扣掉 429。

## 3. 发现并修复的问题

| # | 问题 | 现象 | 修复 |
|---|---|---|---|
| 1 | 订单服务连接池太小，下单事务里夹着 gRPC 调用，连接从头占到尾 | R1 P99 15 秒；R3 950 个请求排队等连接 | 连接池 15 → 40；`CreateOrderCommand` 自己管事务，远程调用都在事务外，事务里只做加锁、复查幂等、写库（#18） |
| 2 | Outbox 每 2 秒取 50 条，每服务每秒最多发 25 条 | 受理 100+ 单/秒，端到端约 4 单/秒；早期约 8 万受理订单只有 273 单完整走完 | 取满一批立刻取下一批（load-test-perf）；一批并发发布、统一保存（#16） |
| 3 | 发布每条消息新开、关闭一个 channel，外层 Polly 重试是同步 `Execute` 套异步方法 | 一条消息和 broker 往返五六次；重试实际不生效 | 常驻发布 channel 池（默认 16，借出期间独占，坏 channel 丢弃重建）；重试改为 `ExecuteAsync`，只重试连接 / channel 瞬时错误（fix/rabbitmq-publisher-channels） |
| 4 | Outbox 领取按 `OccurredOnUtc` 排序，但索引里没有这一列 | 积压越多每次领取越慢，几万条积压时每秒只能发约 100 条 | `Outbox__BatchSize` 调到 500，把领取成本分摊到更多消息上（配置） |
| 5 | 积压时提交库存晚于预占过期 | 已付款订单的库存被释放，`CommitInventory` 进死信 | 预占过期 = 支付截止 + 30 分钟宽限期；过了截止时间的下单消息直接拒绝（load-test-perf）；预占已释放时补扣或转人工（#14） |
| 6 | Saga 每 5 分钟无限重发 | 积压超过 5 分钟后补偿消息自我放大，越积越多 | 重发改为 5 → 10 → 20 → 40 分钟指数退避，上限 60 分钟（#16） |
| 7 | 网关限流排在认证之前 | 全站共用一个限流桶，超过 100 请求/秒就返回 503 | 先认证再按用户限流，拒绝返回 429（load-test-perf） |
| 8 | 共用的 fanout 死信交换机 | 一条死信被复制进所有服务的死信队列，后台重放会重复投递 | fanout DLX → direct 路由交换机，按队列名路由到各自的死信队列（fix/rabbitmq-dlx-routing） |
| 9 | BFF 令牌刷新是一把全进程锁 | 全站每秒只能刷新约 3 个令牌，集中过期时请求排队 20 秒 | 按会话分到 64 把锁，不同用户并行刷新（#17） |
| 10 | 下单请求没有入口限流 | 过载时请求全部挤到连接池前，后台的 Outbox 和消费者拿不到连接 | 全局并发上限（默认连接池上限的 60%）+ 有界队列 200，满了返回 429（#18） |
| 11 | 订单、支付、库存服务单线程消费 | `msa.ordering` 1.77 万、`msa.payment` 7 千积压 | 消费并发 4，预取 64；处理器靠行锁 / 咨询锁保证同一订单、同一用户串行（#14、#19） |
| 12 | `OrderFulfillmentStatusChanged` 没有订阅方 | 每单发布都被 RabbitMQ 退回，Outbox 反复重试、日志刷屏 | 通知服务订阅；只在发货、签收、退回时发布，每单少发 2 条（#16） |
| 13 | EF Core 每条 SQL 打 Information 日志 | 拖慢服务，Loki（384M）被冲垮 | `Microsoft.EntityFrameworkCore` 日志降到 Warning |
| 14 | 无 swap，容器内存上限之和远超物理内存 | 压测时整机卡死，只能控制台重启 | 加 4G swap、`vm.swappiness=10`；压测时停掉 ES；订单服务内存上限单独设为 1G |
| 15 | 压测准备方式导致令牌集中过期 | 每轮开头第 40～70 秒卡顿 | k6 下单前自动预热，每个用户先 GET 一次（#19） |
| 16 | 支付页对已取消的订单一直轮询支付单 | 页面一直转圈、反复 404 | 先轮询订单状态，进入待支付后才查支付单（fix/payment-page-polling） |

## 5. 结论

- **容量**：4C8G 单机全量部署时，订单分散在多个商品上（R9，更接近真实情况），下单在 **约 50～60 单/秒** 以内 P95 < 500ms；单个热点 SKU 时约 70 单/秒。超过这个负载，全局并发上限把多余请求以 429 拒绝，系统不超时、不崩溃。
- **稳定性是这次最大的收获**：同样 2 倍过载，从"大量超时、整机卡死"变成"零超时、零 5xx、快速失败"，压力消失后后台积压能自行清空。
- **瓶颈在机器资源**：后几轮里，前端受理、Outbox 发布、库存和订单的消费都在抢同一台机器的 4 个核。哪一段变快，别的段就变慢一点（R8 发布变快后积压移到库存；R9 库存真正并行后受理变少），总量上不去。代码层面的优化在这台机器上已经基本到头。
- **单 SKU 与多 SKU 的差异**：库存服务按 SKU 加咨询锁保证不超卖，同一个 SKU 的预占、提交只能串行。热点商品（秒杀）场景下库存处理是主要瓶颈；订单分散时库存能并行，但会和其他服务抢 CPU。

## 6. 再往上需要什么

1. **拆分部署**：PostgreSQL、RabbitMQ、监控挪到独立机器，应用机只跑 .NET 服务。
2. **订单服务多实例**：受理和 Outbox 发布都能水平扩展（Outbox 领取用 `FOR UPDATE SKIP LOCKED`，多实例天然分摊）。
3. **Outbox 领取索引**：给 Outbox 表加部分索引 `(OccurredOnUtc, Id) WHERE Status IN (0, 1)`，领取速度不再随积压量变慢（未做，需要各服务生成迁移）。
4. **热点 SKU**：秒杀场景可以用库存分桶，或者 Redis 预扣 + 异步落库，减少同一 SKU 的串行等待。
